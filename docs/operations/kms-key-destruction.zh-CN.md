# KMS 密钥销毁

[English](kms-key-destruction.md) | 简体中文

**适用场景：** 退役一把 KMS 密钥；判断某把密钥保护的数据能否被永久变为不可恢复；响应数据擦除请求或密钥泄露事件；解释为什么一把已计划删除的密钥仍然存在。
**事实来源：** `crates/kms/src/manager.rs`（`delete_key_inner`、`check_deletion_request`、`refuse_referenced_immediate_deletion`）、`crates/kms/src/deletion_worker.rs`（后台清扫及其指标）、`crates/kms/src/types.rs`（`*_PENDING_DELETION_WINDOW_DAYS`）、`crates/kms/src/backends/{local,vault,vault_transit,aws}.rs`（`delete_key`、`remove_expired_key`）、`rustfs/src/kms_deletion_gate.rs`（配置引用）、`rustfs/src/admin/handlers/kms_keys.rs`（`DeleteKmsKeyHandler`）。

销毁 KMS 密钥是一项产品特性，而不是运维操作的副作用：RustFS 靠它在不重写数据本身的前提下，让数据永久不可恢复。本页说明这项特性保证什么、一把密钥要经过哪些步骤，以及围绕它的保护措施。相关文档（英文）：[KMS admin API contract](kms-admin-contract.md)（路由与 IAM 动作）、[KMS backend security properties](kms-backend-security.md)（密钥材料存放位置、版本保留）、[Per-key KMS authorization](kms-per-key-authorization.md)、[KMS observability runbook](kms-observability-runbook.md)。

## 销毁意味着什么

每个 SSE-KMS 对象，以及 SSE-S3 密钥由 KMS 提供的部署中的每个 SSE-S3 对象，都用各自的数据密钥加密；这把数据密钥只以被包裹的形式（用某把 KMS 密钥加密后）保存在对象旁边。销毁 KMS 密钥，就去掉了解开这些数据密钥的唯一手段。对象的字节仍在磁盘上，已有的副本和分层数据也仍在原处，但再也没有任何东西能解密它们。这就是密码学擦除。

这项特性服务于逻辑删除做不到的三类需求：

- **擦除义务。** 租户退场，或者一次删除请求必须覆盖每一份拷贝——包括逐个定位并覆写代价高昂甚至不可能的历史版本、副本和分层数据。
- **密钥泄露。** 可能已泄露的密钥材料，在其下的数据完成重新包裹或被判定放弃之后，被永久退役。
- **介质退役。** 无法逐块擦除的介质，改为销毁密钥使其不可读。

一把密钥通常保护着大量对象，所以销毁它是 KMS 管理 API 中后果最重的操作。下面每一条规则都由此而来。

## 保证

- **密钥永远不会一步销毁。** 销毁必须先经过 `PendingDeletion`：在这个状态下密钥仍然存在，其下的对象仍然可读，删除仍然可以取消。没有任何单个请求能把 `Enabled` 或 `Disabled` 的密钥直接变为已销毁。
- **成功即如实。** 计划删除的请求成功，意味着什么都没有被销毁。销毁请求成功，意味着密钥确实已销毁：响应返回时，密钥记录及其保留的每一个材料版本都已从后端消失。做不到所请求之事的请求会被拒绝，绝不会被悄悄改成另一种操作。
- **销毁不可逆。** RustFS 不保留已销毁材料的任何副本，也不提供撤销删除。销毁之后只可能从本特性之外的备份中恢复（见[销毁不覆盖什么](#销毁不覆盖什么)）。
- **仍被配置引用的密钥不会被销毁。** 作为 KMS 服务默认密钥的密钥，或者被任意桶的默认加密配置指名的密钥，不会被销毁——后台清扫不会，按请求销毁也不会。
- **每个决定都有记录。** 计划删除、取消、销毁以及每一次拒绝，都连同调用者身份写入 KMS 审计日志；后台清扫执行的销毁记录为内部操作。

## 生命周期

| 状态 | 进入方式 | 新的加密 | 读取已有对象 | 离开方式 |
| --- | --- | --- | --- | --- |
| `Enabled` | 创建密钥、启用、取消删除 | 允许 | 允许 | 禁用、计划删除 |
| `Disabled` | 禁用 | 拒绝 | 允许 | 启用、计划删除 |
| `PendingDeletion` | 计划删除 | 拒绝 | 允许 | 取消删除、销毁 |
| 已销毁 | 等待期届满，或加急销毁 | — | 永久失败 | — |

在 `Disabled` 和 `PendingDeletion` 状态下读取照常工作，这是有意为之：只有数据还在、缺失才会被察觉，等待期才算得上安全网。AWS KMS 后端是例外——AWS 自身会拒绝用已禁用和待删除的密钥解密，见[后端差异](#后端差异)。

销毁之后，读取任何用该密钥加密的对象都会以 `400 KMS.NotFoundException` 失败，该密钥 ID 在管理 API 上返回 `404`。这个名字可以再次使用，但之后用同名创建的是一把拥有全新材料的新密钥：它不会让旧对象重新可读。

## 第一步：计划删除

`DELETE /rustfs/admin/v3/kms/keys/delete` 携带指名 `key_id` 的 JSON 请求体，把 `Enabled` 或 `Disabled` 的密钥置为 `PendingDeletion`，并记录截止时间。

- `pending_window_in_days` 设定等待期，必须在 7 到 30 天之间，默认 30 天；超出范围以 `400` 拒绝。
- 响应携带 `deletion_date`（此时间之后密钥才有资格被销毁）和 `impact`（当时发现的配置引用）。
- 允许对仍被配置引用的密钥计划删除。这不销毁任何东西，而且在真正销毁之前会重新检查引用。请把非空的 `impact` 当作截止时间之前需要清理的事项清单。
- 对已处于 `PendingDeletion` 的密钥再次计划删除会以 `400` 拒绝；要修改截止时间请先取消。

请利用等待期确认没有任何东西仍然依赖这把密钥：留意那些没有它就会失败的读取，把桶默认加密改到别的密钥上；如果数据必须比密钥活得更久，运行[批量 rekey 清扫](../architecture/kms-bulk-rekey-contract.md)。

## 第二步：取消，或等待期届满

`POST /rustfs/admin/v3/kms/keys/cancel-deletion` 把 `PendingDeletion` 的密钥恢复为 `Enabled` 并清除截止时间。在密钥被销毁之前的任何时刻都有效；销毁一旦开始即失败。

如果截止时间已过而没有取消，后台清扫会销毁密钥。清扫在每个节点上大约每分钟运行一次，无需运维介入，可以并发运行，也可以在重启后重复运行。对每把到期的密钥，它都会重新检查当时的配置引用和密钥状态：

- **仍被引用：** 密钥保持 `PendingDeletion`，仍可读、仍可取消，并在之后每一轮清扫中被重新考虑；引用消失后即被销毁。因此，一把迟迟没有被销毁的密钥是需要处理的信号，而不是需要重试的故障。
- **期间被取消：** 取消优先，不销毁任何东西。
- **销毁被中断**（崩溃、后端故障）：密钥会处于不可用状态而不是半存在状态，下一轮清扫完成移除。

## 加急销毁

当等不到截止时间时——擦除期限将至、泄露已确认——可以按请求销毁一把已处于 `PendingDeletion` 的密钥，无需等待其截止时间。同一个 `DELETE` 路由接受 `force_immediate: true`。

除非以下条件全部满足，否则加急销毁会被拒绝：

| 条件 | 不满足时 |
| --- | --- |
| 服务端以 `RUSTFS_KMS_ALLOW_IMMEDIATE_DELETION=true` 运行 | `400` |
| 请求使用 JSON 请求体；不接受查询字符串形式 | `400` |
| `confirm_key_id` 与 `key_id` 完全一致 | `400` |
| 密钥已处于 `PendingDeletion` | `400`；请先计划删除 |
| 没有任何桶的默认加密配置指名该密钥，且它不是 KMS 服务默认密钥 | `409 Conflict` |
| 后端支持物理删除密钥 | `501` |

加急销毁缩短的是等待，而不是去掉可取消的那一步。计划删除和销毁是两个独立的、各自被审计的操作，所以单次误操作或恶意调用最坏也只能把密钥停放在一个 `cancel-deletion` 可以撤销的状态。

正常运行时请保持 `RUSTFS_KMS_ALLOW_IMMEDIATE_DELETION` 关闭，只在一次有计划的销毁期间打开。开关关闭时，无论调用者拥有什么权限，等待期都是通往销毁的唯一途径。

## 保护措施及其边界

| 保护措施 | 防范什么 | 做不到什么 |
| --- | --- | --- |
| 强制的 `PendingDeletion` 步骤 | 单个请求销毁数据 | 阻止两次有意为之的请求 |
| 等待期（7–30 天） | 密钥没了之后才发现依赖 | 告诉你哪些对象在用这把密钥 |
| 配置引用检查 | 销毁一把新写入仍在指向的密钥 | 看到已经用该密钥加密的对象 |
| 加急销毁的服务端开关 | 持有 `kms:DeleteKey` 的凭据自行跳过等待期 | 运维打开之后继续生效 |
| `confirm_key_id` | 因输错或重放的请求而操作了错误的密钥 | 自身授予任何权限 |
| 针对指名密钥校验的 `kms:DeleteKey` | 对该密钥没有授权的调用者 | 区分计划删除与销毁；二者以及取消都使用同一个动作 |

引用检查有意只覆盖配置层。RustFS 不维护"哪些对象由哪把密钥加密"的清单，所以空的 `impact` 报告绝不意味着密钥没人用。已经写在某把密钥之下的对象，恰恰就是销毁要使其不可读的东西；这是不是期望的结果，由运维决定，等待期就是用来核实这一点的。

## 销毁不覆盖什么

- **RustFS 控制范围之外的密钥副本。** Vault 快照与存储备份、Local 后端密钥目录的备份，以及通过管理 API 生成的 KMS 备份，都可能仍然持有密钥材料。只有这些副本按各自的流程过期或销毁之后，擦除才算完成。
- **其他密钥。** 销毁之前已被 rekey 清扫重新包裹到另一把密钥上的对象，仍可凭那把密钥读取。每个复制站点各自持有自己的被包裹数据密钥和自己的 KMS；在一个站点销毁密钥不影响其他站点。
- **已在使用中的数据密钥。** 在销毁完成之前已经解开数据密钥的请求可以执行完毕。节点也可能在短时间内继续提供缓存的密钥元数据；如果需要立刻切断，请清除 KMS 缓存。
- **明文与其他加密模式。** SSE-C 对象依赖客户端持有的密钥，未加密对象不依赖任何密钥。
- **磁盘上的字节。** 密文不会被移除。要回收空间请照常删除对象。

## 后端差异

| 后端 | 计划与取消 | 等待期届满后的销毁 | 加急销毁 | 移除的内容 |
| --- | --- | --- | --- | --- |
| Local | 支持 | 后台清扫 | 支持 | 密钥文件 |
| Vault KV2 | 支持 | 后台清扫 | 支持 | 密钥记录及其下的每一条版本记录 |
| Vault Transit | 支持 | 后台清扫 | 支持 | Transit 密钥及其元数据记录；RustFS 在删除前一刻为该 Transit 密钥设置 `deletion_allowed` |
| AWS KMS | 支持；等待期由 AWS 掌管 | 由 AWS 执行 | 不支持（`501`） | 由 AWS 决定；取消后密钥回到 `Disabled`，且整个待删除期间读取都会被拒绝 |
| Static | 不支持 | — | — | 无；该密钥是配置，不是受管密钥 |

在 Vault 后端上，RustFS 使用的凭据需要对密钥路径拥有删除权限，销毁才能成功，见 [KMS backend security properties](kms-backend-security.md)。缺少该权限时，计划删除可以成功，而销毁会在清扫时失败并持续重试。

## 可观测性

- `rustfs_kms_pending_deletion_keys`——已计划且尚未到期的密钥数。截止时间之后数值迟迟不降，说明销毁被阻止或正在失败。
- `rustfs_kms_deletion_tombstone_keys`——销毁被中断、等待下一轮清扫的密钥数。预期在几轮清扫内回到零。
- `rustfs_kms_deletion_sweep_keys_total{outcome}`——`removed`、`blocked`（仍被引用）、`skipped`（已取消或尚未到期）、`failed`、`unreadable`。请对持续出现的 `blocked` 或 `failed` 告警。

每当清扫拒绝销毁一把到期的密钥，服务端日志都会写明该密钥及其引用。部分密钥不可读时各个 gauge 的表现，见 [KMS observability runbook](kms-observability-runbook.md)。

## 操作流程

**退役一把不再需要的密钥。** 把所有桶的默认加密从该密钥上移走；如果它是服务默认密钥，更换服务默认密钥。对必须保留的数据执行 rekey。计划删除，并阅读响应中的 `impact`。等待期内留意失败的读取。让清扫销毁密钥，然后确认该密钥 ID 返回 `404`。

**在期限前擦除数据。** 按上面的方式计划删除并清除所有引用。到期当天，打开 `RUSTFS_KMS_ALLOW_IMMEDIATE_DELETION`，发送携带 `confirm_key_id` 的加急请求，确认该密钥 ID 返回 `404`、读取受影响对象以 `KMS.NotFoundException` 失败，然后重新关闭开关。让仍持有该密钥的备份过期。

**撤销一次计划删除。** 在截止时间之前发送 `cancel-deletion`。在 AWS KMS 上，之后还需启用该密钥。
